# 3. Теоретические сведения

## 3.1. Модульное тестирование

Модульное тестирование — это метод проверки программного обеспечения, при котором отдельные части программы проверяются независимо друг от друга.

Для реализации тестирования используется библиотека **Google Test**.

Она предоставляет следующие возможности:

- создание отдельных тестовых сценариев;
- проверка ожидаемых и фактических значений;
- параметризованное тестирование;
- группировка тестов;
- автоматическое формирование результатов тестирования.

В работе используются основные макросы:

| Макрос | Назначение |
|---|---|
| `TEST()` | Создание обычного теста |
| `TEST_P()` | Создание параметризованного теста |
| `EXPECT_EQ()` | Проверка равенства значений |
| `EXPECT_NEAR()` | Проверка чисел с заданной погрешностью |
| `EXPECT_TRUE()` | Проверка истинности условия |
| `EXPECT_FALSE()` | Проверка ложности условия |

## 3.2. Устойчивость дискретных систем

Дискретная система называется асимптотически устойчивой, если её выходная переменная стремится к равновесному значению при отсутствии внешнего воздействия.

Для линейной дискретной системы устойчивость определяется расположением корней характеристического уравнения.

Система является устойчивой, если все корни характеристического уравнения находятся строго внутри единичной окружности комплексной плоскости:

$$
|z_i| < 1
$$

Для проверки устойчивости в программе реализована функция `checkDiscreteStability()`.

Она принимает коэффициенты характеристического полинома и определяет, находятся ли его корни внутри единичной окружности.

# 4. Реализация математических моделей

## 4.1. Общий базовый класс Model

Для организации моделей используется абстрактный базовый класс `Model`.

Он содержит три виртуальных метода:

- `calculateNext()` — вычисляет следующее значение выходной переменной;
- `getName()` — возвращает название модели;
- `reset()` — сбрасывает внутреннее состояние модели.

Каждая конкретная модель наследуется от базового класса и реализует собственные вычисления.

## 4.2. Модель 1.10

Модель описывается следующим уравнением:

$$
y_{k+1}=a_1y_k+b_1u_k+b_2u_{k-2}
$$

где:

- $y_k$ — текущее значение выходной переменной;
- $u_k$ — текущее управляющее воздействие;
- $u_{k-2}$ — управляющее воздействие с задержкой в два шага;
- $a_1, b_1, b_2$ — параметры модели.

Особенность данной модели заключается в наличии задержанного управляющего воздействия.

Для реализации задержки используются две внутренние переменные, хранящие предыдущие значения входного сигнала.

При отсутствии внешнего воздействия уравнение принимает вид:

$$
y_{k+1}=a_1y_k
$$

Характеристическое уравнение:

$$
z-a_1=0
$$

Условие устойчивости:

$$
|a_1|<1
$$

## 4.3. Модель 2.4

Модель описывается нелинейным уравнением:

$$
y_{k+1}=ay_k\cos(y_k)+b\ln(1+|u_k|)
$$

где:

- $a,b$ — параметры модели;
- $y_k$ — текущее значение выходной переменной;
- $u_k$ — входное воздействие.

В данной модели используются косинусоидальная и логарифмическая функции.

Модель является нелинейной, поскольку содержит произведение переменной $y_k$ на $\cos(y_k)$.

Для анализа локальной устойчивости около нулевого равновесия используется линеаризация. Производная по выходной переменной в нуле равна \(a\), поэтому локальное условие устойчивости имеет вид:

$$
|a|<1
$$

Данное условие относится к локальной устойчивости около нулевого равновесия и не гарантирует глобальную устойчивость модели.

## 4.4. Модель 3.8

Модель описывается дифференциальным уравнением:

$$
\frac{dy}{dt}=-a_1y-a_2y^2+bu
$$

Для численного решения используется метод Эйлера:

$$
y_{k+1}=y_k+\Delta t(-a_1y_k-a_2y_k^2+bu_k)
$$

где:

- $a_1,a_2,b$ — параметры модели;
- $\Delta t$ — шаг интегрирования;
- $y_k$ — текущее значение выходной переменной;
- $u_k$ — входное воздействие.

Для анализа локальной устойчивости около нулевого равновесия используется линеаризация:

$$
z=1-\Delta t a_1
$$

Условие локальной устойчивости:

$$
|1-\Delta t a_1|<1
$$

# 5. Реализация проверки устойчивости

Для проверки устойчивости реализована функция:

```cpp
bool checkDiscreteStability(const std::vector<double>& coeffs);
```

Функция принимает вектор коэффициентов характеристического полинома.

Для определения корней используется численный метод Дюранда — Кернера.

Основные этапы работы алгоритма:

1. Получение коэффициентов характеристического полинома.
2. Нормализация коэффициентов.
3. Начальное приближение корней.
4. Последовательное уточнение корней.
5. Проверка сходимости алгоритма.
6. Определение устойчивости системы по расположению найденных корней.

Если все корни находятся внутри единичной окружности, функция возвращает `true`.

В противном случае возвращается `false`.

В программе проверка устойчивости моделей выполняется с использованием соответствующих характеристических полиномов или локальных линеаризаций.

# 7. Реализация модульного тестирования

Для проверки программы используется библиотека Google Test.

Тесты разделены на несколько групп.

## 7.1. Тестирование функции проверки устойчивости

Проверяются следующие ситуации:

- устойчивый характеристический полином;
- неустойчивый характеристический полином;
- полином с корнями на границе единичной окружности;
- полином с нулевым корнем.

Это позволяет проверить корректность определения устойчивости в различных случаях.

## 7.2. Параметризованное тестирование модели 1.10

Для модели 1.10 используется параметризованное тестирование.

В тесты передаются различные наборы параметров и входных воздействий.

Проверяется, что вычисленное значение выходной переменной соответствует ожидаемому результату.

Также проверяется корректность работы задержки управляющего воздействия.

## 7.3. Тестирование модели 2.4

Для модели 2.4 проверяется правильность вычислений с использованием логарифмической и косинусоидальной функций.

В качестве тестового сценария используются заранее заданные параметры и входные значения.

## 7.4. Тестирование модели 3.8

Для модели 3.8 проверяется правильность вычисления следующего значения переменной с использованием метода Эйлера.

Проверяется соответствие результата математической формуле модели.

## 7.5. Тестирование входных сигналов

В программе предусмотрено три типа входных сигналов:

1. Ступенчатый сигнал.
2. Импульсный сигнал.
3. Гармонический сигнал.

Для проверки используется функция `getInput()`.

Проверяется правильность формирования каждого типа сигнала при различных значениях времени.

## 7.6. Проверка сброса состояния модели

Дополнительно проверяется метод `reset()` модели 1.10.

После вызова данного метода внутренние переменные задержки должны принимать нулевые значения.

Это позволяет убедиться, что модель можно повторно использовать с чистым начальным состоянием.

# 8. Сборка проекта и запуск тестов

Для автоматизации сборки и тестирования используется CMake и командный файл `run_tests.bat`.

CMake отвечает за настройку проекта, компиляцию исходного кода и подключение библиотеки Google Test.

Командный файл выполняет следующие действия:

1. Переходит в корневую папку проекта.
2. Создаёт папку `build`, если она отсутствует.
3. Выполняет конфигурацию проекта с помощью CMake.
4. Компилирует программу и тесты.
5. Запускает модульные тесты через CTest.
6. Сохраняет результаты тестирования в `test_report.txt`.
7. Запускает инструмент OpenCppCoverage для формирования отчёта о покрытии кода.
8. Открывает HTML-отчёт в браузере, если его удалось создать.

Для запуска достаточно открыть файл:

```text
run_tests.bat
```

После выполнения сборки и тестирования результаты сохраняются в соответствующих файлах и папках проекта.

# 9. Анализ результатов тестирования

После запуска автоматизированного тестирования необходимо проверить результаты выполнения всех тестовых сценариев.

В консоли CTest отображается количество успешно пройденных и не пройденных тестов.

В файле `test_report.txt` сохраняется подробный результат выполнения тестирования.

Для анализа покрытия исходного кода используется OpenCppCoverage.

Результат формируется в HTML-формате и сохраняется в папке:

```text
CoverageReport/
```

Основной файл отчёта:

```text
CoverageReport/index.html
```

В отчёте можно просмотреть, какие участки исходного кода были выполнены во время тестирования.

**Фактические результаты тестирования:**

| Показатель | Результат |
|---|---|
| Общее количество тестов | Заполнить по результатам CTest |
| Успешно пройденные тесты | Заполнить по результатам CTest |
| Не пройденные тесты | Заполнить по результатам CTest |
| Покрытие строк кода | Заполнить по OpenCppCoverage |

Числовые результаты необходимо внести после фактического запуска программы, чтобы не указывать неподтверждённые значения.
